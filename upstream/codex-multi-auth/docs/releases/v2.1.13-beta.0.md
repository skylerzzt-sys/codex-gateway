# v2.1.13-beta.0

Makes the pinned-account `503` explain itself.

```bash
npm i -g codex-multi-auth@beta
```

## What changed

When you pin an account and it's unavailable, you get a `503` with `codex_pinned_account_unavailable`. That error now tells you *why*:

```
Pinned account 2 is currently unavailable (rate-limited); run ...
```

The response body carries a structured `reason` field and a full `account_skip_reasons` map keyed by account index — the same shape the pool-exhausted `503` already used, so anything consuming these can branch on one payload across both.

When the reason genuinely isn't known, it comes back as an explicit `null` and gets recorded in `status.lastError`, rather than being flattened to `"unknown"`. That way a mismatch between what `forecast` thinks and what the runtime is doing becomes visible instead of being quietly papered over.

## Known issue

This doesn't fix the [#486](https://github.com/ndycode/codex-multi-auth/issues/486) root cause — `doctor` reporting all green while the runtime still returns `503`.

If you can reproduce that, it would help a lot to run with `ENABLE_PLUGIN_REQUEST_LOGGING=1` and attach the new `503` body plus the logs from `~/.codex/multi-auth/logs/codex-plugin/`.
