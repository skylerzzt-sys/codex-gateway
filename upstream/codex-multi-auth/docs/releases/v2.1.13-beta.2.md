# v2.1.13-beta.2

Stops rotation from cascading through your accounts and getting them all invalidated.

```bash
npm i -g codex-multi-auth@beta
```

## The problem

This is the root cause of [#495](https://github.com/ndycode/codex-multi-auth/issues/495).

When an account's OAuth token came back `401`, rotation moved to the next account and tried again. That's the right behaviour for an expired token — but not for an *invalidated* one. Presenting each account's token from the same IP in quick succession looks exactly like abuse, and OpenAI's anti-abuse detection responded by invalidating them one after another.

So a single invalidated token could take your whole pool with it.

## What's fixed

The `401` handler now reads the response body and looks for explicit invalidation wording — `invalidated oauth token`, `authentication token has been invalidated` — and treats that differently from a generic expired-token `401`.

On invalidation:

- **The `401` goes straight back to you** instead of rotating to the next account.
- **The account gets a 5-minute cooldown** rather than the generic 30-second one (`CODEX_AUTH_TOKEN_INVALIDATION_COOLDOWN_MS`). The cooldown only ever extends, so a racing generic `401` can't cut it short.
- **Session affinity is cleared**, so your next request can pick a healthy account.

Generic `401`s — expired tokens, wrong credentials — still rotate exactly as before.

Both invalidation paths now return the same error shape, `{ error: { message, code: "token_invalidated" } }`, preserving the upstream message when there is one.

## Also new

**`minRotationIntervalMs`** (default 60s, `CODEX_AUTH_MIN_ROTATION_INTERVAL_MS`) gives the last-served account a scoring boost, so back-to-back requests are less likely to present a different OAuth token from the same IP inside that window. The anchor refreshes on every successful request, not just when the account changes.

## Known issue

This does **not** fix [#486](https://github.com/ndycode/codex-multi-auth/issues/486) — `doctor` reporting all green while the runtime still returns `503`.
